## Assumptions

Each assumption is a working choice, taken so that an artefact could be drawn. Each is
reversible and needs confirmation. None of them closes a question above.

| ID | Assumption | Why it was needed | Confirm with |
| --- | --- | --- | --- |
| `A-01` | The bank is an ASPSP offering payment accounts to retail PSUs under PSD2 | Frames the whole analysis | product |
| `A-02` | Finologee is TPP-facing and the bank adapts to its contract (open-host service upstream) | Context-map power; the C4 edge | architecture, Finologee |
| `A-03` | The bank app on a CIAM-enrolled device is the PSU's SCA instrument | Every authorisation flow | iam |
| `A-04` | The target is NextGenPSD2 v1.3.16, the version supplied | All contracts | architecture |
| `A-05` | Retail PSUs first: no corporate accounts and no multilevel SCA in the MVP | Scope | product |
| `A-06` | JSON only: no pain.001, camt or MT94x | The OpenAPI profile | product |
| `A-07` | Errors use the `tppMessages` variant (§4.13.3.1) | The `Error` schema | architecture (`Q-25`) |
| `A-08` | The login screen is a **CIAM browser page**, and the OTP, QR, biometric screens and the consent confirmation panel are **app screens on the enrolled device**. This is the reading of `C-06` that lets the journey be drawn at all | Journey map, blueprint, every sequence | iam, product (`Q-12`) |
| `A-09` | Test data uses the specification's own example values (IBANs `DE40100100103307118608`, `DE02100100109307118603`; `organizationIdentifier` `PSDES-BDE-3DFD21`; ids `123cons456`, `1234-wertiq-983`, `123auth456`). The **labels** "Sandbox AISP Ltd", "Sandbox PISP Ltd", "PSU-1234" and "PSDFR-ACPR-12345" are invented placeholders, not domain facts | Concrete examples | QA |
| `A-10` | A DCP stub is acceptable for WS-01 | The skeleton can run before `Q-05` is answered | architecture |
| `A-11` | Combined AIS/PIS sessions (§9) are not offered in the MVP | R-CNS-07 | product |
| `A-12` | The bank IAM team owns Transmit and PingFederate configuration | `.ddd` owners | iam |
| `A-13` | IBAN is the only account reference type in the MVP | OpenAPI `AccountReference` | product |
| `A-14` | The PSU has a device enrolled with the CIAM before using a TPP; enrolment is a bank-wide capability outside the XS2A scope | The flows assume a device can be reached | product, iam (`Q-36`) |
| `A-15` | The **consent confirmation panel** is the ASPSP "displaying the consent details to the PSU when performing the SCA" of the Detailed Consent model (`SRC-IG` §6). This is what makes the TPP-managed consent screen and the bank-side panel consistent rather than contradictory | The AIS journey; `R-SCA-02` | compliance |
| `A-16` | The gateway keeps an **enforcing projection** of the Finologee-mastered consent record, so that an account read can be decided inside the bank. Whether that projection or the vendor record is authoritative on a read is `D-01`, not this assumption | `RM-ACCESS-DECISION`; the `.ddm`; every read sequence | architecture (`D-01`) |
| `A-17` | Transmit signs the assertion that SCA happened; the ASPSP gateway trusts a PingFederate token obtained by exchanging it | `D-02`; `INV-AUT-05` | iam (`Q-16`) |
| `A-18` | `scaRedirect` lands on a CIAM-hosted bank page rather than a Finologee-hosted one | `SCR-CIAM-LOGIN`; `D-05` | architecture (`Q-47`) |

## Hypotheses (product)

| ID | Hypothesis | Where it is tested |
| --- | --- | --- |
| `H-01` | PSUs abandon the authorisation at the hand-over from the browser to the enrolled device | The MVP learning hypothesis |
| `H-02` | PSUs do not recognise a TPP's legal name when it differs from its brand | MVP UX evidence |
| `H-03` | PSUs expect a withdrawal to stop the TPP immediately | MVP UX evidence; `RM-ACCESS-DECISION` |
| `H-04` | PSUs cannot tell from `ACTC` whether money has left the account | Later (depends on `Q-31`) |
| `H-05` | A PSU who revokes on the **TPP's** consent screen believes they have revoked at the **bank**, and does not look for a bank surface | MVP UX evidence; feeds `D-09` |
