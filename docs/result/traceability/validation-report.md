## 1. How this was run

The repository's validator hard-codes the `docs/` and `tests/` prefixes of the artefact contract.
This proposal is staged under `docs/result/`, which mirrors that layout, so the validator was run
with `docs/result/` mounted as its root. Every path printed below and every path inside the
artefacts is relative to that root; on acceptance the pack is promoted to the repository root and
the paths become literal.

Two further deviations, both stated so that nobody mistakes them for a clean bill:

- `docs/ai/tools/validate.py` imports `dsl` and `examplemap_to_feature`; the files are now named `dslcheck.py` and `em_to_feature.py`. They were run under their imported names.
- The generated `.feature` files carry the header `# generator: tools/sdlc/examplemap_to_feature.py`, a path that no longer exists — the tool lives at `docs/ai/tools/em_to_feature.py`. The string is emitted by the tool itself and the validator compares the projection byte for byte, so it cannot be corrected by hand: it is a one-line fix in `em_to_feature.py`, recorded here as `W-TOOL-01`.
- `LIKEC4_JSON` was produced by a **local metadata extractor**, not by `likec4 export json`, because the LikeC4 toolchain could not be installed here (§3). The extractor reads only the `metadata { … }` blocks and the element nesting; it is not a LikeC4 parser, and the model's own grammar is therefore **unverified**.

## 8. Findings against the domain model

| ID | Finding | Reading |
| --- | --- | --- |
| `W-DDD-01` | No subdomain is classified `core` | Deliberate. XS2A here is a regulatory obligation assembled from bought products — Finologee mediates TPPs *and* masters the consent record, Transmit and PingFederate carry identity, DCP holds the money. The classification is a budget, and claiming `core` would be a budget claim nobody has made. Domain experts should push back if this is wrong, because it is a statement about where the bank invests |
| `W-DDD-02` | `TPP Access -> Consent` is labelled **conformist**, not `anticorruption-layer` like its sibling edges | Deliberate, and the least comfortable line on the map. An anticorruption layer protects a model the bank owns; the bank does not own the consent record. If `D-01` moves the master record into the gateway, this edge becomes `customer-supplier` and the `.ddd` must change with it |
| `W-DDM-01` | "Authorising a new recurring consent ends the former one" (§6.3.1.1) spans two `Consent` aggregates and is therefore a policy, not an invariant | Correct and deliberate. Making it transactional would need a "PSU–TPP relationship" aggregate, a boundary nobody has asked for. The resulting status is `Q-20` |
| `W-DDM-02` | `INV-CNS-06` refuses a read when the bank's projection is past an agreed bound — but the bound itself is not in the model | Deliberate. The bound is `D-01`, and a model may not assert a number nobody has agreed |

## 9. Assumptions carried by these artefacts

Eighteen, in [`questions-and-assumptions.md`](questions-and-assumptions.md). Four are doing more
work than the rest and should be read before anything is approved:

- `A-08` — the login screen is a CIAM **browser** page and the OTP, QR, biometric and consent panels are **app** screens. Without it `C-06` cannot be drawn at all.
- `A-15` — the consent confirmation panel **is** the ASPSP displaying consent details during SCA, per the Detailed Consent model. It is what makes the ADR and the specification agree on the AIS side; if it is wrong, the AIS journey is as unsettled as the PIS one.
- `A-16` — the bank keeps an enforcing projection of the vendor-mastered consent record. It is drawn everywhere; `D-01` decides whether it is authoritative.
- `A-17` — Transmit signs the SCA assertion and the gateway trusts a PingFederate token obtained from it. It carries `INV-AUT-05`.
