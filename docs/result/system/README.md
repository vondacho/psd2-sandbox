# Solution design proposal — PSD2 XS2A interface

> **Status:** proposal generated by AI, branch `proposal/xs2a-solution-design`. Architects and
> engineers review sections 3–6 (gate G4). Everything marked **Recommendation** is an AI
> recommendation and **not a decision**: the decisions in §4 belong to the people named in each
> "Decides" row.

## 1. Scope

This proposal covers the XS2A interface the bank owes TPPs under PSD2, specified by Berlin Group
NextGenPSD2 v1.3.16 (`SRC-IG`), built around the products and decisions in
[`docs/context/adr.md`](../../context/adr.md) (`SRC-ADR`).

It covers AIS on dedicated accounts and single SEPA credit transfers with redirect SCA. It does
**not** design signing baskets, bulk or periodic payments, card accounts, funds confirmation
(`Q-21`), multilevel SCA, the embedded SCA approach or the resource status notification service.
Those stay as unscheduled stories on the
[story map](../stories/xs2a-access-to-account.storymap).

## 2. What the bank has already decided (`SRC-ADR`)

| Element | Fact | Open |
| --- | --- | --- |
| ASPSP XS2A gateway | Built in house; must comply with PSD2 | Everything about its shape |
| Finologee | The PSD2 gateway: sits between ASPSP and TPP, OIDC and OAuth 2.0 towards the TPP, **and manages the consent state** | Its integration contract (`Q-03`); how the bank enforces a consent it does not master (`D-01`); whether it publishes revocation events and an audit export (`Q-45`) |
| Transmit | Bank CIAM: device management and enrolment, Auth-N, Auth-Z, SCA methods; **token issuer**; the browser **login screen** | Factor categories (`Q-14`); how it reaches the app (`Q-15`); who signs the SCA assertion (`Q-16`) |
| PingFederate | Bank IDP and **token issuer**. DCP services consume PingFederate tokens; a **token exchange** converts a Transmit token into one | Whether the exchange exists and who calls it (`D-02`, `Q-04`) |
| Mobile app | Presents the OTP, QR-code and biometric screens and the **consent confirmation panel**, on the enrolled device at the CIAM's request | What it presents for a payment — nothing is named (`Q-17`) |
| DCP | In-house core banking: accounts, transactions, payment services | Its interfaces (`Q-05`); its booking behaviour (`Q-31`) |
| Consent screen | **Managed by the TPP**, in the web browser, where the PSU grants or revokes access | A revocation towards the ASPSP has no surface (`D-09`) |

Three of those rows changed this design more than anything else, and §3.2a explains what they
cost.

### 3.2a What the revised context costs, stated plainly

**The bank has one browser surface.** `SRC-ADR` gives the consent screen to the TPP and the login
screen to the CIAM. Everything the PSU confirms happens on the enrolled device. Three browser
pages between login and return — waiting, outcome, unavailable — are **proposed by this design and
not stated by any source** (`Q-18`). If the bank declines them, the PSU is returned to the TPP
with no bank-side feedback at all, and `UX-05` and `UX-08` have nowhere to live.

**The AIS journey is compliant by construction; the PIS journey is not, yet.** The consent
confirmation panel is exactly what §6 expects of an ASPSP under the Detailed Consent model
(`A-15`), so the AIS side is sound. For a payment, `SRC-ADR` names no surface, so nothing shows
the amount and the payee — and dynamic linking has nothing to bind to (`C-09`). This design does
not invent that screen. `RM-PAYMENT-APPROVAL` and `getPaymentApproval` exist, marked
`x-conditional-on: Q-17`, and `STORY-PIS-PAYMENT-CONFIRM` sits unscheduled on the map.

**The bank enforces a consent it does not master.** Finologee holds the consent record, and
`SRC-IG` holds the ASPSP answerable for `consentStatus`, for the access decision on every read and
for `ACCESS_EXCEEDED` (`C-08`). `INV-CNS-06` is written so that a projection the bank cannot vouch
for refuses the read rather than serving it — but the staleness bound behind that is `D-01`, not a
fact this design may assert. `RSK-07` is the risk it creates.

**A PSU cannot withdraw access at the bank.** The only consent screen is the TPP's, so a
withdrawal there is `terminatedByTpp`. `revokedByPsu` is defined as a revocation towards the ASPSP
(§14.15) and has no path in (`C-07`). `D-09` decides whether that gap is acceptable;
`JRN-ACCESS-CONTROL.S3` is left in the journey map as a stage with no touchpoint so the gap stays
visible.

## 4. Decisions that need human authority

### D-01 — Enforcing a consent the bank does not master

| | |
| --- | --- |
| Decides | Architecture board, with compliance |
| Question | `SRC-ADR` puts the consent state at Finologee. `SRC-IG` makes the ASPSP answerable for the access decision on every read. Which copy decides, and how stale may the bank's copy be? |
| Options | **A** call Finologee on every read · **B** projection kept current by vendor-pushed changes, with a staleness bound and a synchronous fallback · **C** projection refreshed by polling |
| **Recommendation** | **B.** A read is on the hot path and a revocation must bite immediately (`H-03`); polling trades one for the other. `INV-CNS-06` refuses a read when the projection is past its bound, so the failure mode is refusing access rather than serving revoked data |
| To verify | `V1` Finologee pushes revocation and expiry (`Q-45`) · `V2` the audit trail can be exported (`Q-45`) · `V3` the synchronous fallback's latency is acceptable |
| Blocks | WS-01 build start |

### D-02 — Token topology between Transmit, PingFederate and DCP

| | |
| --- | --- |
| Decides | Architecture board with IAM |
| Question | `SRC-ADR` states that DCP consumes PingFederate tokens and that a Transmit token must be exchanged. It does not say who performs the exchange, with which grant, or how often |
| Options | **A** the gateway calls DCP with the Transmit token (contradicts `SRC-ADR`) · **B** RFC 8693 token exchange at PingFederate, called by the core banking adapter · **C** the CIAM federates to PingFederate and hands out a PingFederate token from the start |
| **Recommendation** | **B**, with a token cached for the PSU session so the exchange is not on every DCP call. **C** is cleaner if PingFederate and Transmit already federate, and should be checked first because it removes a hop |
| To verify | `V1` PingFederate supports the exchange (`Q-04`) · `V2` token lifetime and caching on the hot path · `V3` sender-constrained tokens · `V4` what DCP does with an expired token mid-journey |
| Blocks | WS-01 (the skeleton exists partly to prove this hop) |

### D-03 — SCA approach(es) offered to TPPs

| | |
| --- | --- |
| Decides | Product and architecture, with compliance |
| Options | **Redirect** to the CIAM login screen · **Decoupled**: no browser at all, the CIAM pushes to the enrolled device · **OAuth2 SCA** · **Embedded** |
| **Proposed answer** | **REDIRECT**, because `SRC-ADR` puts a login screen in the browser (§5.1.1, §6.1.1.1). But note honestly that **decoupled** (§5.1.7) is what the rest of the journey already is: every confirmation happens on the enrolled device, and the browser does nothing after login. If `Q-18` is answered "no bank pages", decoupled becomes the better fit and the TPP-facing contract changes with it. Embedded is incompatible with the device journey as written |
| Blocks | WS-01 scenario; `EXMAP-SCA-DEVICE`; the `ASPSP-SCA-Approach` header |

### D-04 — Propagating status changes between contexts

| | |
| --- | --- |
| Decides | Engineering lead |

### D-09 — Where a PSU withdraws access towards the ASPSP

| | |
| --- | --- |
| Decides | Compliance and product |
| Question | `SRC-ADR` gives the consent screen to the TPP. A withdrawal there is `terminatedByTpp`; `revokedByPsu` is a revocation towards the ASPSP (§14.15) and has no surface (`C-07`) |
| Options | **A** add a bank surface — but the bank has only the CIAM login screen to hang it on · **B** surface it in the bank's existing online or mobile banking channels, outside this design · **C** accept that only the TPP can end a consent, and defend that to the supervisor |
| **Recommendation** | None. This is a compliance judgement about what PSD2 requires of the bank, not an architecture trade-off, and the supplied sources do not settle it. `STORY-PSU-REVOKE` stays unscheduled and `RM-PSU-TPP-ACCESS` stays without a consumer until it is answered |
| Blocks | Go-live (`D-08`) |

## 5. Quality attributes and operability (proposal)

| Concern | Proposal | Evidence expected |
| --- | --- | --- |
| Traceability of calls | `X-Request-ID` on every request, span and event (`API-XS2A-EVENTS` envelope) | `EVID-WS-TRACE` |
| Security | mTLS at the edge; no credential or confirmation code stored readable (`INV-AUT-04`); the SCA result bound to what the PSU confirmed (`INV-AUT-05`) | Security review of WS-01 |
| Data protection | No IBAN or core identifier in a path (`INV-ACC-01`); account data read through, not stored | Contract test on `resourceId` |
| Consent correctness | Every read decided against the consent, and refused when the projection is past its bound (`INV-CNS-06`) | `EVID-MVP-CONSENTS` |
| Availability and performance | No targets supplied (`Q-01`, `OBJ-04`). Measure p95 latency and availability per operation from WS-01 onwards | `EVID-MVP-OPS` |
| Authorisation conversion | Share of consents reaching `valid`; share of authorisations `finalised` against `failed`, split by surface | `EVID-MVP-SCA-CONVERSION` |

## 6. Risks

| ID | Risk | Mitigation proposed |
| --- | --- | --- |
| `RSK-01` | Finologee's integration contract constrains the resource model more than assumed (`A-02`, `Q-03`) | Put the vendor contract and the consent projection first in the walking skeleton |
| `RSK-02` | Transmit and PingFederate cannot bind the SCA to what the PSU confirmed, so dynamic linking fails (`INV-AUT-05`) | Capability check inside WS-01, before any UI work |
| `RSK-03` | DCP's read and submit interfaces are slow, missing or token-incompatible (`Q-05`, `D-02`) | Core adapter stub in WS-01, real interface in MVP-01, anticorruption layer throughout |
| `RSK-04` | The MVP omits a mandatory endpoint — funds confirmation (`Q-21`) | Compliance decision before go-live (`D-08`) |
| `RSK-05` | The Berlin Group licence (CC BY-ND) restricts publishing a derived profile (`Q-07`) | Legal review before this repository is shared outside the bank |
| `RSK-06` | Two surfaces and often two devices — browser login, then the enrolled device — increase drop-off (`H-01`) | `UX-08`; measure login → confirmation drop-off in `RM-OPS-SCA-FUNNEL` from WS-01 onwards |
| `RSK-07` | The bank answers for a consent record it does not hold. A revocation at the vendor that does not reach the gateway means the bank serves data the PSU withdrew — a regulatory failure with the bank's name on it (`C-08`, `D-01`) | `INV-CNS-06` fails closed; verify the vendor's push and audit export (`Q-45`) before WS-01 is called done |
| `RSK-08` | A payment is confirmed on a surface that never showed its amount or payee (`C-09`, `Q-17`) | Do not ship PIS to production until `Q-17` is answered; `STORY-PIS-PAYMENT-CONFIRM` is the story that closes it |
