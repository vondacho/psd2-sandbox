# D-02 — Token topology between Transmit, PingFederate and DCP

> **Status:** proposal generated by AI. The recommendation is not a decision. Decides:
> architecture board with IAM.

## What `SRC-ADR` establishes

Three statements, all facts for this design:

1. **Transmit is a token issuer.** It authenticates the PSU on the login screen and drives the SCA methods on the enrolled device.
2. **PingFederate is a token issuer**, and **DCP services require a PingFederate token to be consumed**.
3. **A token exchange is required** to convert a Transmit token into a PingFederate one.

What the ADR does not say is who performs the exchange, with which mechanism, how often, and what
happens when it fails mid-journey. That is this decision. A fourth token is in the picture and
outside it: whatever Finologee issues to the TPP, which never reaches DCP.

Drawn in [`../uml/sequence/d-02-token-topology.puml`](../uml/sequence/d-02-token-topology.puml).

## Options

### A — The gateway calls DCP with the Transmit token

- **Against:** it contradicts statement 2 of `SRC-ADR`. Listed only so that the option is on the record as refused, not overlooked.

### B — RFC 8693 token exchange at PingFederate, called by the core banking adapter

`CMP-CORE-ADAPTER` exchanges the CIAM token for a PingFederate token over mTLS and caches it for
the PSU's session.

- **For:** one place in the code knows about the exchange, and it is the same place that already adapts to DCP. The gateway's other modules never see either token.
- **Against:** a hop on the path to core banking. If PingFederate cannot do RFC 8693, this option disappears (`Q-04`).

### C — The CIAM federates to PingFederate, and the journey carries a PingFederate token from the start

Transmit is configured as an identity provider PingFederate trusts, and the token that arrives at
the gateway is already one DCP accepts.

- **For:** no exchange on the hot path at all; one token type inside the bank.
- **Against:** it needs a federation that may not exist, and it makes every PSU authentication cross both products, which changes the failure modes of the login screen itself.

## Recommendation

**B**, and **check C first**, because C removes the hop entirely and the two products are both in
house. If the IAM team confirms an existing Transmit → PingFederate federation, C is the better
answer and B becomes the fallback.

Whichever is chosen, one thing should not be: the ASPSP gateway must trust **one** issuer for the
authority it acts on. Today the sources leave it ambiguous whether the assertion that SCA happened
comes from Transmit or from PingFederate (`Q-16`). `A-17` assumes Transmit signs and the gateway
trusts a PingFederate token obtained from it. That assumption is doing real work in `INV-AUT-05`
and should be confirmed early.

## What must be verified

| | Verification | Why it decides |
| --- | --- | --- |
| `V1` | PingFederate supports RFC 8693 token exchange, or an equivalent (`Q-04`) | B depends on it |
| `V2` | Whether a Transmit → PingFederate federation already exists | It decides between B and C |
| `V3` | Token lifetime against the length of a PSU journey, and what a mid-journey expiry does to a payment that has already been confirmed | An expiry after SCA but before submission is the worst failure this design has |
| `V4` | Whether bank tokens are sender-constrained | Otherwise a leaked token is a bearer of DCP authority |

## Consequences

- The `.ddd` records `Core Banking -> Customer Identity and SCA` as **conformist**: DCP's token requirement is not negotiable, so the identity estate adapts. That label should change only if DCP's requirement changes.
- `RSK-08` in the system README tracks the hot-path cost.
- The walking skeleton exists in part to prove this hop with a real token, not a stub (`EVID-WS-TOKEN`).
