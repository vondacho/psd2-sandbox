# Solution design proposal — PSD2 XS2A interface

> **Status:** proposal generated by AI, branch `proposal/xs2a-solution-design`. Architects and
> engineers review sections 3–6 (gate G4). Everything marked **Recommendation** is an AI
> recommendation and **not a decision**: the decisions in §4 belong to the people named in each
> "Decides" row.

## 1. Scope

This proposal covers the XS2A interface the bank owes TPPs under PSD2, specified by Berlin
Group NextGenPSD2 v1.3.16 (`SRC-IG`), built around the products and decisions in
[`docs/context/adr.md`](../context/adr.md) (`SRC-ADR`).

It covers AIS on dedicated accounts and single SEPA credit transfers with redirect SCA. It
does **not** design:

- signing baskets, bulk or periodic payments;
- card accounts;
- funds confirmation (`Q-14`);
- multilevel SCA;
- the embedded SCA approach;
- the resource status notification service.

Those stay as unscheduled stories on the [story map](../stories/xs2a-access-to-account.storymap).

### 3.2a PSU screens and read models

The [service blueprint](../journeys/service-blueprint.md) defines every PSU-facing screen
(`SCR-*`) and every read model (`RM-*`), each with its consumer, decision, data, owner and
consistency need. There are **three bank surfaces**:

| Surface | Managed by | Screens |
| --- | --- | --- |
| Login screen | `CMP-PING` (the IDP, in-house) | `SCR-IDP-LOGIN` |
| Consent screen (browser) | `CMP-CONSENT-SCREEN` — managed by the Bank ASPSP (`SRC-ADR`) | Grant access, wait for the app, outcome, request unavailable, no enrolled device (unscheduled), manage this TPP's access, withdraw confirmation |
| SCA screen (bank app) | `CMP-MOBILE-APP`, presented on demand by `CMP-TRANSMIT` | `SCR-APP-SCA`, plus device enrolment (unscheduled, `A-16`) |

Consequences worth stating:

- **A payment has no browser approval page.** Amount and payee are shown on the SCA screen, where the PSU "confirms his identity and his consent" (`Q-46`, `Q-48`). The browser only carries login, waiting and outcome.
- **The subject digest** still binds what the PSU approved to what SCA signs (`INV-AUT-05`), now across three surfaces.
- **`CMP-PSU-CHANNEL-API`** is the consent-screen backend (`x-conditional-on: D-01` marks the operations whose *implementation* changes under `D-01` Buy, where they call Finologee); it always serves the app's SCA prompt.
- **Consistency needs are unchanged:** strong for `RM-ACCESS-DECISION` (revocation) and `RM-REDIRECT-SESSION` (single use); eventual for the two scheduled ones.

## 4. Decisions that need human authority

### D-01 — Consent state: make or buy (`SRC-EVAL`)

Evaluated in full in [`decisions/d-01-consent-management.md`](decisions/d-01-consent-management.md):
11 weighted criteria, both options scored.

| | |
| --- | --- |
| Decides | Architecture board, with product and compliance |
| Options | **Make** — ASPSP gateway, IDP and CIAM · **Buy** — Finologee's built-in consent management |
| **Recommendation** | **Make.** The decisive criteria are that the bank must answer "may this TPP read this account now?" without calling a vendor, and that a revocation must bite on the TPP's next read. Buy wins on standard fit and time to market; those are recoverable, vendor-held consent state is not |
| Conditions | A two-day verification of the Buy option (revocation propagation, white-label domain, audit export, OIDC delegation to Ping) before committing; write the consent example maps as acceptance tests first; keep screen and state separable |
| Blocks | WS-01 build start |

### D-02 — Token compatibility between Finologee and Ping (`SRC-Q`)

| | |
| --- | --- |
Answered in full in [`decisions/d-02-token-compatibility.md`](decisions/d-02-token-compatibility.md),
with the options drawn in [`d-02-token-options.puml`](uml/sequence/d-02-token-options.puml).

| | |
| --- | --- |
| Decides | Architecture board with IAM |
| Options | **A** the gateway accepts the Finologee token · **B** exchange it for a Ping token · **C** no token inside: mTLS plus a signed request context |
| **Recommendation** | **B.** Keep two trust domains and bridge them once, with RFC 8693 token exchange at Ping over mTLS, so the gateway trusts a single issuer. **A** is not recommended: it makes a vendor an issuer for bank APIs. **C** is the fallback if Ping cannot do the exchange |
| To verify | `V1` Ping supports RFC 8693 · `V2` Finologee can call it · `V3` token lifetime and caching on the hot path · `V4` sender-constrained bank tokens |
| Blocks | WS-01 (the skeleton exists to prove this hop) |

### D-03 — SCA approach(es) offered to TPPs (`Q-03`)

| | |
| --- | --- |
| Decides | Product and architecture, with compliance |
| Options | Redirect to the consent screen · OAuth2 SCA · Decoupled (no consent screen; push to the app) · Embedded |
| **Proposed answer** | **REDIRECT.** `SRC-ADR` puts the login screen and the consent screen in the web browser and SCA in the bank app, which is the Redirect SCA approach (§5.1.3, §6.1.1.1). These are bank pages the TPP redirects to, not components embedded in the TPP application. Decoupled and embedded are not offered; OAuth 2.0 stays between the TPP and Finologee. Compliance confirms against [EBA-OP2], which was not supplied (`Q-03`) |
| Blocks | WS-01 scenario, example maps `EXMAP-SCA-REDIRECT-APP` and `EXMAP-PIS-*` |

### How SCA is split across the three surfaces — settled by `SRC-ADR`

Not a decision this proposal needs to take. The PSU authenticates on the **IDP login screen**, and
the **CIAM** then asks the **bank app** to present the **SCA screen** on an enrolled device, where
the PSU confirms his identity with the final authentication method. The app implements the SCA
methods (MFA, biometrics, OTP).

What is still open sits in the ledger rather than here: which factor category each step
contributes and whether they are independent under the RTS (`Q-45`), who signs the SCA assertion
the gateway trusts (`Q-07`, proposed: Ping, `A-18`), and what a PSU without an enrolled device is
offered (`Q-21`, `Q-49`).

## 5. Quality attributes and operability (proposal)

| Concern | Proposal | Evidence expected |
| --- | --- | --- |
| Traceability of calls | `X-Request-ID` on every request, span and event (`API-XS2A-EVENTS` envelope) | `EVID-WS-TRACE` |
| Security | mTLS at the edge; the resource store holds no raw credentials; confirmation codes stored hashed (`INV-AUT-04`) | Security review of WS-01 |

| Consent conversion | Share of consents reaching `valid`; share of authorisations `finalised` vs `failed` | `EVID-MVP-SCA-CONVERSION` |

## 6. Risks

| ID | Risk | Mitigation proposed |
| --- | --- | --- |
| `RSK-01` | Finologee's integration contract constrains the resource model more than assumed (`A-02`) | Put the vendor contract and the token hop first in the walking skeleton |
| `RSK-02` | Ping/Transmit cannot bind SCA to the approved subject (dynamic linking) | Capability check inside WS-01 (`INV-AUT-05`) |
| `RSK-03` | Core banking read/submit interfaces are slow or missing (`Q-06`) | Core adapter stub in WS-01, real interface in MVP-01; anticorruption layer |
| `RSK-04` | The MVP omits a mandatory endpoint (funds confirmation, `Q-14`) | Compliance decision before go-live (`D-08`) |
| `RSK-06` | Three surfaces and often two devices — login and consent in the browser, SCA in the app — increase drop-off (`H-01`) | `UX-08`; measure approve → last-factor drop-off in `RM-OPS-SCA-FUNNEL` from WS-01 onwards |
| `RSK-08` | Token exchange (`D-02`) adds a hop on every forwarded TPP request; if Ping cannot do RFC 8693 the fallback changes the integration late | Verify `V1` in WS-01 preparation; cache bank tokens per (TPP, consent) |
| `RSK-05` | The Berlin Group licence (CC BY-ND) restricts publishing a derived profile (`Q-23`) | Legal review before this repo is shared outside the bank |
