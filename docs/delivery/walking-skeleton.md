## Technical learning objective

Prove, with the thinnest possible behaviour, that a request from a licensed TPP can travel the
**whole** bank path and come back — deployed by the pipeline, and observable end to end.

1. **The TPP edge.** A test TPP with a test QWAC reaches Finologee over mTLS. Finologee identifies it and forwards the request to the ASPSP gateway carrying a **Ping-issued token obtained by exchange** (`D-02`), over a contract that is still unknown (`Q-04`). *This is the least-known hop and the main reason for the skeleton* (`RSK-01`, `RSK-08`).
2. **The SCA path**, across three surfaces:
   - `scaRedirect` takes the PSU to the **IDP login screen** (Ping), in the browser;
   - for a consent, the PSU then approves on the **consent screen**, managed by the Bank ASPSP (`SRC-ADR`; `D-01` decides where the consent *state* lives);
   - the **CIAM** asks the **bank app** to present the **SCA screen** on the enrolled device, where the PSU confirms identity;
   - **for a payment, the surface that shows the amount and payee is not defined** (`Q-46`). WS-01 cannot prove dynamic linking end to end until the bank names it; it proves the digest binding with the payment details carried in `RM-SCA-PROMPT` as a placeholder;
   - the SCA result finalises the authorisation, bound to the approved subject (`A-18`, `Q-07`, `RSK-02`, `INV-AUT-05`).
3. **The resource model.** A consent gates an account read (`INV-CNS-06`), and a payment moves `RCVD` → `ACTC` once authorised.
4. **The delivery path.** Commit → build → contract tests → deploy to a test environment → the automated scenarios below, each with one trace.

Business value is deliberately limited: one account, one payment, test data only.

## Screens and read models

The minimum that makes the SCA path walk, from the
[service blueprint](../journeys/service-blueprint.md):

- `SCR-IDP-LOGIN` — Ping, an existing bank capability;
- `SCR-CONSENT-ACCESS` — minimal: TPP name, accounts, approve or decline;
- `SCR-CONSENT-AWAIT-APP`;
- `SCR-APP-SCA` — identity confirmation; it carries the amount and payee in this build only as the placeholder answer to `Q-46`.

After the SCA screen answers, the browser returns straight to the TPP; the outcome screen comes
in MVP-01. The read models needed are `RM-REDIRECT-SESSION`, `RM-SCA-CONTEXT`,
`RM-CONSENT-APPROVAL`, `RM-PAYMENT-APPROVAL`, `RM-AUTHORISATION-OUTCOME`, `RM-SCA-PROMPT` and
`RM-ACCESS-DECISION`.

Two things WS-01 must prove are technical, not UX:

- the `subjectDigest` served with an approval read model is the one the SCA screen binds, across the browser and the enrolled device (`INV-AUT-05`);
- the token bridge of `D-02` works on a forwarded request.

## Components and interfaces

- **Components** — LikeC4 view `walkingSkeleton`:
  - external and vendor: `CMP-TPP` (test TPP harness), `CMP-FINOLOGEE-GW`;
  - ASPSP gateway modules: `CMP-XS2A-ADAPTER`, `CMP-CONSENT`, `CMP-AUTHORISATION`, `CMP-PAYMENT`, `CMP-ACCOUNT-INFO`, `CMP-CORE-ADAPTER` (**stub**), `CMP-XS2A-STORE`;
  - channel and identity: `CMP-PING` (login screen, token exchange), `CMP-CONSENT-SCREEN` (Bank ASPSP, `SRC-ADR`), `CMP-TRANSMIT` (enrolled device, SCA trigger), `CMP-MOBILE-APP` (SCA screen), and `CMP-PSU-CHANNEL-API` — `resolveRedirectSession`, `getApprovalRequest`, `decideApprovalRequest`, `getAuthorisationOutcome` and `getScaPrompt`; under `D-01` Buy the first four call Finologee instead of the bank's own consent store.
- **Interfaces** — the `API-XS2A-PROFILE` operations tagged `x-delivery: WS-01`:
  - consents: `createConsent`, `getConsentStatus`, `getConsentScaStatus`, `deleteConsent`;
  - accounts: `getAccountList`;
  - payments: `initiatePayment`, `getPaymentInitiationStatus`, `getPaymentInitiationScaStatus`.

## Deployment path (proposal — the platform is unknown, `Q-22`)

1. The single ASPSP gateway deployable (`D-06`) is built on every trunk commit.
2. The pipeline runs unit tests (the `INV-*` invariants) and contract tests.
3. It deploys automatically to a test environment connected to Finologee's test tenant, a Ping test tenant (login screen and token exchange), a Transmit test tenant with an enrolled device, and a test build of the mobile app.
4. The pipeline triggers the `@WS-01` acceptance scenarios against that environment.
5. No production deployment is part of WS-01.

## Contract-validation approach

- `API-XS2A-PROFILE` is linted in CI (Redocly, `openapi-spec-validator`).
- Schema-driven conformance tests run the WS-01 operations against the deployed gateway, both through Finologee and directly at the adapter. A property-based tool such as Schemathesis is one option; the choice belongs to engineering.
- **Compatibility:** diff the profile against the official Berlin Group v1.3.16 OpenAPI file (`W-API-02`). Narrowing is intentional and documented; widening is a defect.
- The Finologee ↔ gateway contract gets its own provider tests as soon as `Q-04` is answered.

## Automated test path

`docs/stories/*.examplemap` → `tools/sdlc/examplemap_to_feature.py` →
`tests/acceptance/features/*.feature` (each file records its source's sha256) → step definitions
driving a test TPP harness with a test QWAC. The step definitions are *to be written*; they are
not part of this proposal.

The PSU steps need an automatable test PSU at Ping and an automatable SCA screen on an enrolled
Transmit test device, or a test-only confirmation hook (`Q-07`, `Q-45`).

## Observability and production evidence

- `X-Request-ID` is the trace correlation id from the TPP harness through Finologee (if it forwards it, `Q-04`), the gateway, the SCA hand-off and the store.
- Minimal metrics: request count, latency and error code per operation; consents by status; authorisations by `scaStatus`.
